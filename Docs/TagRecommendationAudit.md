# 本地标签推荐审查与升级

审查日期：2026-10-15。范围：Apple 与 Android 的分类消费、推荐工具、语义撞库回退。

## 审查结论

原有固定 taxonomy 有 796 个标签，覆盖情绪、场景、主题、类型、风格、人声、乐器、质感、节奏，以及九项数值特征。仅 25 个条目带别名，Android 未消费这些别名，日常说法与专业术语之间存在检索缺口；推荐消费也没有完整表达复合意图：

| 原有路径 | 对推荐效果的影响 | 本次调整 |
| --- | --- | --- |
| Apple `recommendByMood` 只用单个 mood/scene 召回，再按艺人/标题排序 | 未利用多维意图与标签相关度 | 共用多维标签排序 |
| Apple 情绪推荐无结果时整库 `shuffled()` | 不相关歌曲也可能冒充场景推荐，最近排除也可能被重新引入 | 移除随机补足，返回真实缺口 |
| 撞库不足只在工具结果里提示模型再调用其它工具 | 补足不稳定，容易忘记跨阶段排除和数量预算 | 有意图标签时 Runtime 自动补足，共用硬约束与艺人/专辑预算 |
| Android 推荐消费入口是单分类列表 | 不能组合“深夜 + 钢琴 + 不悲伤 + 低能量” | 增加跨维度 `recommend_by_tags` |
| 原有结构化标签 SQL 按匹配数/置信度截断，缺少重排 | 同艺人、同专辑和相近内容容易集中 | 新推荐路径完整读取有效候选，再评分、去重、重排 |

分类本身仍是模型根据提供的元数据/证据推断，并非完整音频测量。增加排序与回退不能纠正所有错误标签；本次不重写已有分类、不提升规则版本，也不要求整库重新消耗模型调用。

## 专业标签与日常用语

增量扩展到 **844 个规范标签、366 个别名**（256 个条目带别名），保留全部既有 ID。情绪 137、场景 134、主题 76、类型 26、风格 301、人声 34、乐器 55、质感 52、节奏 29。新增番茄钟、下班放松、一人食、哄睡、游戏时、手作等生活场景，以及 Organic House、Amapiano、双簧管、手碟、Clave 节奏等专业标签。

同一概念的说法归一到同一 ID，例如自习/学习、纯音乐/无歌词/无人声、后摇/Post-Rock、钢琴独奏/Solo Piano、爵士说唱/Jazz Rap；不为同义说法新建规范标签。英文大小写、全半角、空白及连字符/下划线的常见差异统一检索。相关但不同的概念（学习与专注、情绪温暖与音色温暖）保留区别；有歧义的名字需要明确 ID，禁止猜测归类。

两端共用相同规范 ID、名称、别名；`python3 Scripts/sync_recommendation_taxonomy.py --check` 与 Android CI 检测词表漂移。分类提示明确每维度可多选，同一歌曲可保留多个有证据的场景/情绪/风格/乐器。分类响应按规范 ID 去重，重复项不占用 64 个有效标签的预算。

别名查询和组合排序对旧分类立即生效。新增规范标签会在后续分类或导入中写入，不会凭空填补旧记录；新词表本身不代表现有曲库已经拥有所有标签，也不声称涵盖所有语言、年代和音乐学属性。

## 两种推荐方式

- **默认方式**：模型按语义生成候选并撞库，同时通过 taxonomy 工具提供偏好标签。真实命中不足时，由本地标签索引自动补足。
- **指定标签方式**：用户明确说“只用本地标签推荐”等，模型直接调用 `recommend_by_tags`，跳过撞库。

推荐结果不自动播放或修改歌单。已有播放、队列、歌单授权与 Runtime 编排保持各自边界。

示例请求：

> 只用本地标签，推荐 20 首适合深夜听的钢琴曲，不要悲伤，能量不要高。

对应结构化意图示例（标签以 taxonomy 工具实际返回为准）：

```json
{
  "includeTags": ["instrument.piano"],
  "preferTags": ["scene.late_night", "mood.calm"],
  "excludeTags": ["mood.sad"],
  "numericRanges": {"energy": [1, 4]},
  "maxPerArtist": 2,
  "maxPerAlbum": 2,
  "limit": 20
}
```

`includeTags` 是同时满足的硬条件；`preferTags` 是评分偏好。偏好不覆盖排除条件，也不解除数值范围。只有偏好、没有正向硬条件时，至少命中一个偏好标签，防止零相关补足；满足正向硬条件的候选可以缺少偏好标签，但排序更低。负向条件单独不足以定义推荐主题。

组合意图支持如下规则，两端的指定推荐与撞库自动回退共用：

| 意图 | 参数 |
| --- | --- |
| 学习且钢琴 | `includeTags: ["scene.study", "instrument.piano"]` |
| 钢琴或木吉他 | `anyTagGroups: [["instrument.piano"], ["instrument.acoustic_guitar"]]` |
| 学习且钢琴，或者深夜且木吉他 | `anyTagGroups: [["scene.study", "instrument.piano"], ["scene.late_night", "instrument.acoustic_guitar"]]` |
| 学习、专注、钢琴中至少符合两项 | `preferTags: ["scene.study", "scene.focus", "instrument.piano"], minimumPreferredMatches: 2` |

`anyTagGroups` **组内 AND、组间 OR**，至少一组完整匹配；同时执行全局 `includeTags`、`excludeTags` 与数值范围。空组、未知标签、非法最少命中数均报错，不能变成全库召回。最多 20 组、每组最多 20 项；规范化后重复标签和重复组合删除。一首歌命中多组仍只返回一次，命中说明列出所有符合的查询标签。

`minimumPreferredMatches` 对不同的规范偏好 ID 计数，默认 0：有正向硬条件时偏好可不命中，否则至少命中一项。显式 N 是硬条件；自习和学习不能重复计为两项。数量不足时报告缺口，不降低 N、不拆开完整组合凑数。

`numericRanges` 使用分类量表：energy=1...10，其余特征=1...5；tempo 不是 BPM。继续推荐或手动补足时，用 `excludeTrackIDs` 传已展示的组合 ID。跨调用没有自动记住“已经听过”的隐式行为画像。

## 排序与数据范围

1. 验证稳定 TagID（未知、有歧义或非法范围报错，不静默忽略）。
2. 只取指定服务器的当前规则版本、当前内容指纹仍有效的索引；排除“不喜欢”。Apple 同时包含真实本地音乐命名空间。Android 沿用其当前活动服务器目录范围。
3. 执行硬标签、排除、数值范围、最低置信度与已展示 ID 筛选。未分类/低置信度特征不能证明满足硬条件。
4. 偏好按维度平衡，使用标签置信度和候选频率权重：75% 的维度平衡相关度 + 25% 的不同查询标签覆盖度。多个独立命中（包括同维度）得到奖励，同义词只计一次；单维度堆标签不会无限抬高分数。只有组合、没有偏好时，按组合内标签评分。评分是排序依据，不是校准后的“适合概率”。
5. 符合硬条件的同录音编码保留高质量版本；不同录音时长使用现有 `TrackQuality.recordingKey` 区分。
6. 用相关度、艺人/专辑重复惩罚、标签重叠冗余做重排，严格执行数量上限。撞库种子计入共享预算；不会放宽上限凑满目标。

新路径不在筛选和排序之前截断为前 50/200 首。Android 读取有效曲目和标签时按 SQLite 参数容量分块。相同候选与参数产生稳定结果；需要继续探索时显式排除此前展示的组合 ID。

## 验证与局限

新增回归覆盖多维优先级、偏好与硬条件区别、完整组合的与/或匹配、多组命中不重复、同维度多命中排序、别名不虚增最少命中数、日常/专业用语归一、多标签分类保留与持久化、组合在撞库/回退两阶段的一致性，以及排除条件、数值范围、低置信度、不随机补足、组合 ID 隔离、输入顺序稳定性、录音去重、撞库种子预算、索引过期/不喜欢与超过 900 条绑定的读取。

Linux 上可以运行 Android 与 Swift 纯排序算法用例；Apple 数据库、Agent 工具和 AppShell 集成测试需要 macOS CI。Linux 聚焦测试包只为 Domain 的 Apple 本地化 API 提供了兼容占位，未替换推荐实现。完整 Apple 构建结论以原生 CI 为准。

当前没有用户实际曲库与听感评分样本，不能把这些回归通过表述为真实推荐满意度已达标。后续听感验收应固定若干复合意图，分别检查硬条件违规率（应为零）、标签贴合度、艺术家/专辑集中度、重复推荐率及不足数量。权重目前是可解释的启发式参数，尚未经真实听感标注调参。

### 大曲库合成验证

Linux 容器 Release 构建，以 20,000 首合成歌曲选择 20 首。最佳多维匹配放在第 20,000 首，结果仍将它排在第一，返回 20 位不同艺人的歌曲。一次重排测得约 4.37 秒；将艺人/专辑归一化与身份键移出重排循环后，同一合成例测得约 1.02 秒。此数据只衡量本机该次内存排序，不含数据库读取、模型请求或真实设备 UI 延迟，不能当作端到端性能保证。
