# 设置中的后台标签分类

标签分类直接调用设置中的模型，将固定标签写入本地索引。任务由应用持有，与助手会话、聊天工具循环及页面生命周期分开。

## 入口与操作

- iOS：设置 → 标签分类。
- macOS：设置 → 资料库与播放 → 标签分类。
- Android 手机 / TV：设置 → 标签分类卡片；曲库中的管理入口也指向设置。

先在大模型设置中配置模型，并保持 AI 与歌曲元数据权限开启。在标签分类中确认“允许发送歌曲元数据进行分类”，然后点击开始/继续。分类授权独立于聊天的首次外发确认；不需要打开助手、建立会话或让模型调用工具。

设置显示当前音乐库已处理、待处理数量、运行状态和错误。暂停只停止未提交的请求，已提交批次保存在 SQLite / Room；继续时重新查询待处理曲目。聊天的停止按钮不影响分类。模型认证、网络、协议错误会显示在设置中，不会把失败批次标记成已完成。

Apple 分类默认从每批 8 首开始，受输出和上下文预算约束，小容量模型会使用更小批次。结果不完整、输出截断或请求无法装入上下文时，按实际失败批次逐级减半，最低 1 首；缩小后本轮保持该批量，避免反复扩批失败。每首歌曲仍独立匹配 ID、校验标签与内容指纹，整批通过后才原子保存，不会将缺失或串入其它歌曲的结果当作成功。

设置说明批处理规则，并显示读取、请求模型、校验、保存、等待重试等阶段，以及当前批次、实际首数、标签组和已等待秒数。单次调用（包括 Provider 内部重试与空响应恢复）默认最多等待 300 秒；这只约束一次请求，任务本身没有总时间限制。超时会取消真实 HTTP 请求，降低下一轮批量，并按 15、30、60 秒逐步退避，最长每 300 秒再试。网络中断、临时服务错误、空响应及暂时无法校验的分类结果也会自动重试，已完成批次不会重做；认证、配置或授权错误会停止并显示具体原因。

临时等待、系统暂停和永久失败会在设置及播放页/应用内提示，最近原因持久保存。手动暂停会清除自动继续意图；临时故障和系统暂停保留意图，回到前台、重新启动恢复同一资料库或获得系统执行时间后自动继续。无需因为某一次请求超时重新点击开始。

Apple 分类遵循已配置 Provider 的传输能力及用户的推理设置：流式端点读取标准事件，明确不支持流式的端点使用普通请求，不再一律强制非流式或遗漏用户选择的推理模式。Chat Completions、Responses 和 Anthropic Messages 均由现有 Provider 编解码。收到正常完成信号后才校验并入库；拒绝、截断、连接中断或工具调用不会被当作已完成分类，推理内容不会写入标签。

正文既可以来自增量，也可以来自最终的完整文本、内容分片或消息快照。快照只补充尚未收到的后缀，按输出及内容分片区分，避免完整 JSON 重复拼接。若正常结束后正文仍为空，会在重新检查授权后向同一 Provider 发起一次普通请求恢复，保留模型和推理设置；恢复也计入同一个单次期限。两次均为空时保留待处理记录，退避后自动重试，仅显示正文/推理长度、输出 token 数和结束原因，不记录或展示模型推理正文，更不会将推理内容当成标签结果。

如果模型没有足够证据而返回空标签，界面会显示未获得标签的数量。“重试无标签曲目”只将这些记录重新排入任务，不影响已有标签，避免“已处理”被误解成“每首都有可用分类”，也无需清空整个索引。

现有有效分类保留，不强制重跑。清空索引和索引包导入/导出仍使用已有设置中的备份操作，不自动删除数据。

## 后台执行

Android 使用进程级任务与 `dataSync` 前台服务，通知显示进度并提供暂停操作。离开设置、切换页面和 Activity 重建不会取消任务。系统限制前台服务时停止运行并保留已完成数据；应用进程被终止后，可以重新打开设置继续。

macOS 使用应用持有的任务并避免 App Nap 中断正在进行的工作。退出应用后任务停止，重新打开后可继续。

iOS 分别跟踪前台、真实音频播放、`BGProcessingTask` 与短期后台执行时间。一个短期执行凭证到期时，若仍在前台、真实音频正在播放或还有 BGProcessing 时间，分类会继续。全部执行条件结束时才取消未提交请求，保留继续意图并请求系统再次调度；回到前台或真实播放恢复后也会自动续接。后台任务只完成一次，旧执行凭证不会覆盖新凭证。手动暂停同时撤销系统调度和自动继续意图。

系统何时调度、是否挂起或终止应用仍由 iOS 决定；不能承诺进程在所有系统状态下始终常驻。分类不会制造静音音频来延长运行时间，也不会改变用户的播放。已提交批次不受系统中断影响。

## 分类与写入链路

1. 校验目标音乐库、AI 开关、歌曲元数据权限和专门的分类授权。
2. 从本地目录读取待处理歌曲，按输出预算选择小批次，默认每批 8 首；容量不足或结果不完整时缩小批次，不需要每次从单首逐步扩批。
3. 只发送歌曲内容元数据与固定标签目录；不发送聊天、歌词、播放历史、收藏、评分、文件路径、流媒体地址或凭据。
4. 模型返回 JSON；拒绝工具调用、外来 ID、重复 ID 和不完整批次。结构不完整时有限缩批重试，到单首仍失败则显示错误。
5. 再次检查授权、目标音乐库和取消状态。
6. 在原子写入边界核对请求时的内容指纹。歌曲在分类期间改名或改变其它内容元数据时拒绝旧响应，不将旧标签盖成最新分类。
7. 写入成功后读取真实数据库状态，再处理下一批。无证据的标签可省略，不强行猜测；索引处理完成不等于模型对每首歌曲都有足够证据给出标签。

Apple 分类请求还会预留输出、协议开销和估算余量。固定标签目录本身约 22 KB，估算超过 5,800 tokens，直接附带全部目录无法适配 4K 上下文。小上下文模型现在按容量分组考虑全部 844 个标签，再归一合并结果，每首整体仍最多 64 个标签；完成全部组才原子保存，失败时不会把不完整的标签组当作完成。无需删减专业标签或日常标签来迁就模型容量。

分类结果沿用固定标签、同义词归一、多标签推荐及撞库回退路径。后台任务本身不播放歌曲或修改歌单。

分类浏览页跟随已提交批次、暂停和完成状态自动刷新，已打开的分类歌曲页也会重新读取结果；后台更新时保留已有列表，避免反复闪现空白加载页。

## 验证

新增用例覆盖文本模型无需工具调用的完整分类链路、千首曲库按 8 首批处理且不漏曲或重复提交、容量不足时从较小批量起步、实际失败批次缩小后不反复扩批、暂停后只处理剩余曲目、取消后的迟到响应、授权撤销和元数据变化。Android 使用本地模拟 HTTP 服务验证真实 Provider 编解码、响应解析与 Room 写入；同时验证标签可被推荐索引消费。Apple 使用 URLProtocol 验证实际 Chat Completions / Responses 编解码、SQLite 入库及组合标签推荐，并模拟服务端不返回、首批 8 首已保存但后续请求卡住；4K 上下文用例检查所有标签仍被送入分类，并能把不同标签组的结果用于同一条 AND 推荐查询。

Linux 可运行 Android 测试与 Swift 语法检查。Apple 数据库与应用集成以原生 CI 为准；系统后台调度时间、通知交互和真实模型的效果仍需设备验证。没有用户的模型凭据或设备曲库，模拟 HTTP 成功不能代表所有实际模型配置都已经实测。
