## 三、关键真实调用链验证（代码证据）

1. **播放链路**：`selectAndPlay` → 取消旧 task → `syncNowPlayingTrack()`（先展示）→ `cacheStore.cachedFileURL` 本地优先 → `engine.play(track)`（AVPlayer）→ 成功后再 `syncNowPlayingTrack()`。所有入口（页面/远程命令/Siri/快捷指令/Agent）最终都进 AppModel。
2. **控制中心**：`SystemMediaIntegrationController.start`（AppModel.init 调用一次）→ 音频会话 + 远程命令 + 中断 + 路由；`NowPlayingCoordinator.update/updateProgress/artworkLoaded` 主线程写 `MPNowPlayingInfoCenter`。
3. **后台**：Info.plist UIBackgroundModes=audio + `.playback` 分类 + allowAirPlay/allowBluetoothHFP + 单例持有 engine；无任何页面生命周期 stop 路径。
4. **恢复**：冷启动 `restorePersistedLibrary` → `restoreLastConnection`（本地快照+aux cache，零网络）→ apply() → `registerAndSync`（后台增量）→ 恢复播放会话（.idle 不出声）。
5. **同步事务**：`beginSync` staging → `completeSync` commit；失败 discard，保留上次数据。
6. **Agent**：`AgentCoordinator.send` → `AgentRunner.run` → LLM 或本地规则 → `AgentToolkit.executeV2` / `SystemToolExecutor` → bridge/systemService → AppModel；确认走 `PendingConfirmation`。

### 1. AI 助手「有多少个歌单」返回 0 + HTTP 400 —— 已修复

从未写入 SQLite；因此 SQLite 歌单恒为 0。模型看到「0 个歌单」后又尝试调用歌单对象工具，
因 `requirePlaylistID` 校验不到 SQLite 中的歌单而失败，进而触发 AI 服务 400 并降级到本地规则。

- `AuralisAppModel` 新增 `persistServerPlaylists(_:serverID:)` / `deleteLocalPlaylist(_:serverID:)`，

- 写入点覆盖全部路径：`apply()`（首次连接 + 冷启动恢复回填）、`refreshAuxiliaryDataInBackground()`（后台/手动刷新）、
  `createPlaylist` / `renamePlaylist` / `addToPlaylist` / `removeFromPlaylist` / `reorderPlaylist` / `deletePlaylist` /
  `loadPlaylistTracks`（歌单详情拉回真实曲目顺序后写回）。
- `LocalCatalogStore` 新增 `deletePlaylist(_:)`（删除歌单 + 曲目关系）；`purgeServer` 补删 `playlist_tracks`。
- 新增测试：`LocalCatalogTests`「Playlist upsert/read-back/delete round trip matches Agent query path」、

## 十五、Agent HTTP 400 / 服务器侧重 + 备份恢复后切换服务器（2026-08-06）

### 1. Agent 工具调用后必然 HTTP 400 → 已修复（根因）

**现象**：问歌单先给出正确结果，紧接着报「AI 服务暂时不可用（服务返回 HTTP 400），已改用本地能力处理」；播放《以父之名》先弹歌又报「未找到可播放的歌曲」。

**根因（代码证据）**：`AgentRunner.runWithLLM` 在工具执行后把 `AIMessage(role: .tool, ...)` 追加进 `conversation`，下一轮请求把 `role: "tool"` 消息发给 OpenAI 兼容 API。本 Agent 不是原生 function calling（没有 assistant `tool_calls`），无 tool_calls 的 `tool` 角色消息会被 DeepSeek / 各中转网关拒绝 → 每轮工具执行后的下一轮请求必 400 → 降级本地规则，看起来「只能搜本地、碰不到服务器」。

**修复**：工具结果一律改用 `role: .user`（带「（工具执行结果）」前缀）回传，消息序列变为合法的 system/user/assistant/user 交替，不再触发 400；LLM 可多轮完成「搜索 → 播放 → 总结」。

### 2. Agent 对服务器侧重 → 提示词重写 + 服务器工具补齐

- `systemPrompt` 重写：明确「服务器是数据源、本地目录是缓存」；新增「服务器优先的操作准则」（本地无结果先查 server_sync_status / server_sync_start，不要把本地没有说成服务器不存在；播放流程 library_search → playback_play_song；歌单/收藏/同步流程）。
- 工具按分组展示（服务器与同步 / 本地库查询 / 播放控制 / 播放队列 / 歌单与收藏 / 推荐与维护），避免 100+ 工具淹没模型；未分组工具简列名称。
- 新增真实实现：`server_list` / `server_get_current` / `server_test_connection` / `server_get_capabilities` / `server_sync_status` / `server_sync_start`（此前注册表有、dispatch 无 case，调用会落到「未实现的工具」）。
- 工具结果回传说明：成功即总结，不重复调用已成功的工具。

### 3. 备份恢复后切换服务器弹「重新添加」→ 已修复

**根因**：恢复备份只写了账号（persistence + Keychain），没有本地资料快照；`ProductionServerConnector.restoreConnection` 要求 `account + snapshot` 都存在，否则返回 nil；`AuralisAppModel.restorePersistedLibrary` 又要求 `!result.tracks.isEmpty` → 双双判失败 → `shouldPresentServerSetup = true` 弹重新添加。

**修复**：
- `restoreConnection`：只要账号存在就返回结果（无快照时返回空库），并始终重建已认证客户端（支撑后台同步）。
- `restorePersistedLibrary`：去掉 `!result.tracks.isEmpty` 条件，仅在没有任何账号时弹重新添加；恢复/切换后由 `registerAndSync` 后台完成首次同步。

- **逐首分类**：`SongTagClassifier` 每批 5-10 首，使用**分类专用系统提示词**（不带聊天历史），为每首提供 稳定ID/歌名/艺术家/专辑/年份/Genre/曲目号/时长/歌词（结构化截取保留开头主歌副歌结尾）/语言/格式/码率/采样率/位深；确定性标签（年代/格式/高解析度/高码率）由 App 直接计算。
- **结构化输出**：严格 JSON，按 songID 对应（不按位置），每首含 11 组标签（每组带 id/confidence/basis）+ confidence + insufficientInformation + reasonSummary。
- **置信度分层**：≥0.8 直接写正式标签；0.5–0.8 写入并标「待复核」；<0.5 仅保留在记录。阈值集中配置（TagConfidencePolicy）。
- **任务状态机 + 断点续传**：`tagging_tasks` 表为每首保存独立状态（pending/processing/succeeded/failed/insufficient/review/userConfirmed）+ 模型/词典版本/提示词版本/元数据摘要/歌词摘要/Token/失败原因/重试次数；重启、崩溃、断网后只继续未完成或失败的歌曲，已成功且资料未变化的不再消耗 Token。
- **重分类判定**：歌词或元数据（标题/艺术家/专辑/Genre/年份）变化、之前失败、词典/提示词版本变化、用户主动要求、完全重建时重新分类；播放次数/收藏/下载只更新动态标签，不调模型。
- **失败处理**：429/5xx/超时有限重试+短暂退避；认证/配置错误（400/401/403/404/未配置 Key/余额不足）立即暂停整个任务并提示，不逐首失败；失败保留队列可重试。
- **Token/费用**：首次完整分类前显示 歌曲数/有歌词/无歌词/批次数/预计 Token 范围/模型/预计耗时，确认后才开始；分类页显示真实进度 x/total、各状态统计、标签总数、当前模型、已消耗 Token、已运行时间。
- **控制**：开始 / 暂停 / 继续 / 取消（保留已完成）/ 重试失败 / 重新分类资料不足 / 完全重建（确认，只替换 AI 标签，保留用户手动标签）。

## 二十四、标签分类调度改为「自动逐批 20 首」（2026-08-06）

### 调度模型
- **每批固定 20 首**：从数据库（SQLite）直接读取下一批未分类歌曲（`pendingClassificationTracks`，LEFT JOIN tagging_tasks 排除 succeeded/userConfirmed，LIMIT 20），**不把全部歌曲载入内存、不预创建全部请求**；最后不足 20 首按实际数量。
- **自动逐批**：批内完成并写入数据库后才进入下一批；批次间等待 1.5 秒；直到全部完成 / 用户暂停取消 / 致命错误。不再需要每 20 首手动点击。
- **20 首 = 一个业务批次**：一次模型调用共享 系统提示词/词典/限制/冲突规则/输出格式；内部按 10 首拆成 API 子请求（若歌词超长），但页面仍按本批 20 首计数；每首按 songID 独立对应。
- **每批完整流程**：固定歌曲 ID → 保存批次开始（taskID/seq/trackIDs/开始时间/阶段）→ 收集歌词 → 提交模型（临时错误指数退避重试 ≤3 次）→ 解析/校验词典/规范化/去重/置信度过滤 → 逐首写入 ai_classification + tagging_tasks → 更新批次统计（成功/失败/不足/复核/Token/耗时）→ 落库批次完成 → 释放本批临时对象 → 自动下一批。
- **断点恢复**：`tagging_batches` 表保存未完成批次；App 关闭/崩溃后启动，先恢复未完成批次（只重处理该批未完成歌曲），完成后再取下一批；已成功歌曲绝不重新提交。
- **失败处理**：单首缺失/格式错误 → 标记失败、保存本批其他有效结果、不补足数量；临时错误（超时/429/5xx/流中断）指数退避重试，超限保存为可重试并进入等待重试；致命错误（Key 无效/认证/模型不存在/余额/Base URL/格式持续不兼容/数据库写入失败/空间不足）**立即停止整个任务**，不制造失败请求。
- **状态分离**：整任务状态（未开始/运行/暂停/等待重试/配置错误停止/取消/完成）+ 当前批次状态（准备数据/请求模型/解析结果/校验标签/写入数据库/批次完成/批次部分失败）。
- **标签统计实时更新**：每完成一批立即刷新 累计已分类/标签数/各标签歌曲数/待复核/失败/不足；标签页运行期间逐渐出现结果。
- **页面**：显示 歌曲总数/任务状态/累计已分类/剩余/失败/不足/待复核/标签数/模型/累计 Token/累计运行 + 当前批次（第 X 批、本批进度 x/20、本批状态、本批 Token、本批耗时、进度条）；按钮 开始自动分类 / 暂停 / 继续 / 取消 / 完全重建 / 重试失败 / 重新分类资料不足。

- CatalogReader 新增：`upsertTaggingBatch` / `latestUnfinishedTaggingBatch` / `pendingClassificationTracks(serverID:limit:)`；`clearTaggingTasks` 同时清批次。

## 二十五、修复 macOS Keychain -128 导致无法连接（2026-08-06）

### 现象
macOS 连接服务器报 "Secure credential storage failed with status -128"（errSecInteractionNotAllowed：Keychain 交互不允许）。

### 根因与修复
1. **测试连接不应写 Keychain**：`ProductionServerConnector.testConnection` 原先用临时 Keychain 凭据构造客户端；macOS 上 Keychain 写入可能返回 -128，导致"测试连接"失败。改为**内存凭据（InMemoryCredentialVault）**：测试连接完全不写 Keychain，测试本就不需要持久化凭据。
2. **正式保存（connect）的 Keychain 兼容**：`SystemKeychainBackend.add` 在 macOS 上若因 `kSecAttrAccessible + kSecAttrSynchronizable` 组合返回 -128，去掉这两个属性重试一次，凭据仍写入系统 Keychain。
3. **macOS entitlements 增加 `keychain-access-groups`**：`$(AppIdentifierPrefix)com.auralis.player.macos`，提升 Keychain 可用性。
4. **错误分类**：`ConnectionErrorDescription` 增加 `CredentialVaultError` 分类——Keychain 被锁/不可用时给出明确提示（"无法访问系统 Keychain（可能被锁定或签名受限）。请解锁 Mac 后重试…"），不再统一显示"连接失败"。

# 标签化撤销 · 恢复流派分类（2026-08-07）

## 背景
此前因「音乐库流派为空」把音乐库分类临时改成了「AI 标签分类」（设置页标签分类 + 逐首大模型打标 + 标签浏览页）。
复盘确认：流派为空并非 App 解析缺陷——Navidrome `getGenres` 的流派名在 **`value` 字段**（Subsonic 规范如此，App 的 `GenreDTO` 一直正确解析，且有单测覆盖），曲目级 `genre`/`genres` 字段也一直解析正确。真正原因是：
1. Mac「流派」列表当时错误地显示 AI 标签（`tagSummaries`）而不是真实流派；
2. iOS 音乐库把「流派」入口换成了「标签」入口。

因此本次：**完全移除 AI 标签分类子系统，恢复并接通「流派」分类**。

## 流派分类接通（本次修复）
- iOS 音乐库：`LibraryScope` 用「流派」替换「标签」；新增 `genreList`——显示 `catalog.genres`（服务器 getGenres + 曲目 genres 双路合并结果），按实际歌曲数降序，点击进入 `.genre(genre)` 流派详情页；空时提示并调用 `refreshGenres()` 回退服务器拉取。
- macOS：`MacLibraryPage` 的 `genreList` 由「显示 AI 标签」改为「显示真实 `catalog.genres`」，同样按歌曲数降序 + 点击进入流派详情。
- 流派数据链路（无需改动，验证正确）：`getGenres`（`value` 字段）→ `GenreDTO` → `catalog.genres`；`getAlbumList2`/`getAlbum`/`getSong` 的 `genre`/`genres` → 每首 Track.genres → `apply()` 推导合并；冷启动从持久化 Track 推导 + `refreshAuxiliaryData` 增量合并。本地 Navidrome 实测：`getGenres` 返回 Jazz/Rock/Ambient/Electronic（value 字段），6 首歌均带 `genre` 与 `genres` 数组。
